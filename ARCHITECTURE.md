# Architecture and boundaries

`gdpl-core` defines the versioned result and adapter-description data types without engine dependencies. `gdpl-hardware` collects host metadata using sysinfo. `gdpl` owns process lifecycle, sampling, and command-line entry points. `gdpl-analyzer` imports selected display intervals from an existing PresentMon CSV and calculates descriptive statistics; it does not collect frames. Raw observations remain in JSON with unit-bearing names and an explicit unavailable list. The wall clock gives run context; elapsed sample time uses a monotonic clock. Results are local and need no service.

The adapter description is a preliminary data contract, not a working transport or SDK. A future protocol must negotiate versions and capabilities, define metric registration, orchestration, errors and cleanup, and specify framing, size limits, timeouts and clock synchronization before implementation. No engine compatibility is claimed.

Current validity is deliberately narrow: only complete duration and at least one usable sample are checked. It does not check repeatability, rendering settings, background interference or thermal state. CPU usage is a per-process interval estimate from the OS; memory is the process resident set/working set as supplied by sysinfo. Captures exclude descendants. Result files use create-new and are flushed; interrupted writes may leave incomplete JSON. Future storage needs atomic, recovery-friendly writes and separation of large raw streams from aggregates.

Frame analysis requires a process ID and swap chain to avoid mixing streams. Missing intervals are counted, while capture coverage and event loss remain unknown. Percentile, low-FPS, and stutter definitions are documented in the README. The imported CSV is external evidence and its provenance is not independently verified. A future live capture backend must establish its own lifecycle, error handling, and measurement coverage without coupling core to an engine.
